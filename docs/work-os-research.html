Anatomy of a Work OS

How the modern all-in-one work platform is actually put together — the object graph, the four configuration engines that sit on top of it, and the order to build them in. Researched from public product documentation and API references, then reduced to something you can implement.

01 / Thesis

It is not a to-do app. It's a configurable database with opinions.

The mistake most people make when rebuilding a platform in this class is treating it as a task manager with extra screens. It isn't. Underneath, there is one object graph — containers holding work items — and four configuration engines that let each customer reshape that graph into their own workflow without a developer.

Everything the marketing site lists — 15+ views, custom statuses, custom fields, automations, dashboards, docs, chat, goals, time tracking, forms, whiteboards, AI — is either one of those engines or a satellite module hanging off the same graph. The product's actual pitch is consolidation: replace the separate tools a team pays for with one workspace where a task, the doc describing it, the chat about it, and the hours logged against it are all the same records.

That has two consequences for your build:

  • The engines are the product, not the features. Shipping a Board view is a weekend. Shipping a view system where any user can define grouping, filters, sort, and visible columns against arbitrary user-defined fields, save it, and share it — that's the actual work, and everything else composes out of it.
  • Breadth is a trap for a solo build. The incumbent's breadth is the result of eight years and a large engineering org. Copying the surface area produces fifteen shallow features. Building the engines properly produces a product that feels deep on day one and grows sideways cheaply.
Read this first

The two hardest problems in this category are permission-aware querying at depth and real-time collaboration on two different kinds of data. Both are architectural, both are extremely expensive to retrofit, and both are covered in The hard parts. Decide them before you write the first migration.

02 / Graph

The hierarchy is the spine everything else attaches to

Containers nest from the organization down to the smallest checkbox. Each level is not just a folder — it is a configuration boundary, and that's the part worth copying. Settings defined higher up flow down and can be overridden lower down.

Workspace
The organization. Billing, seats, members, roles, integrations, audit log. One per company. Everything above this is your SaaS account model, not the product.
└─Everything view
A virtual level, not a container — cross-workspace views that query every list the viewer can see. Falls out for free if your view engine is written against a query, not a parent id.
└─Space
Department or major function. The main configuration boundary: statuses, which features are enabled, custom fields, privacy, default views.
   └─Folder
Optional grouping of lists — a client, a quarter, a product area. Inherits statuses from the Space, can override.
      └─Subfolder
One further nesting level, added late in the incumbent's life and given its own permissions, statuses, fields, and automations. Design for arbitrary depth from day one and you avoid this retrofit entirely.
      └─List
Where work actually lives. Can sit directly in a Space (folderless) or inside a Folder. Owns the custom fields and status set that its tasks resolve against.
         └─Task
The atomic work item. Has a home list but can appear in several lists at once — status and custom fields always resolve from home.
            └─Subtask
A task with a parent. Same table, same fields, same everything. Nests up to seven levels deep in the incumbent.
               └─Checklist item
Deliberately not a task: no assignee semantics worth speaking of, no status, no reporting. A cheap nested list for steps nobody needs to track. Keep it cheap.

The rules that actually matter

  • Subtasks are tasks. One table with a self-referential parent_id. Never model them separately — every feature you build for tasks would need building twice.
  • Lists can be parentless within a Space. Your foreign keys need to allow a list whose parent is a Space rather than a Folder. Model the container chain polymorphically or you'll write two of every query.
  • Configuration inherits and overrides. A list's effective status set is its own, else its folder's, else its space's. Resolve this once in a cached service, not ad hoc in twelve places.
  • A task can live in many lists. This single feature breaks the naive tasks.list_id column. It needs a join table, with one row flagged as home. Decide now — retrofitting it means rewriting every query in the app.

Custom task types

A late but important addition: tasks carry a type (Task, Bug, Feature, Lead…), and custom fields can be scoped to a type, so a Bug loads bug fields and nothing else. This is what keeps a mature workspace from drowning in forty irrelevant columns. It costs one nullable column on the task and a scope table on the field — build it early, because retro-fitting field scoping is painful.

04 / Engines

Four engines sit on the graph

Every configuration surface in the product reduces to one of these. They share a shape: a definition attached to a container, an inheritance rule, and a resolver that answers “what applies to this object for this user?”

Status engine Field engine View engine Permission engine
04.1

Status engine

Statuses are user-defined strings, but they are not free-form: every status belongs to a group, and the group is what the rest of the system reasons about. “Done” means group = done, not name = "Done".

not_started  · optional active done closed  · terminal
  • Groups are fixed; statuses within them are not. A team can have six active statuses named anything. Reporting, filters, “show closed”, and completion percentages all key off the group.
  • Closed is special. In the incumbent it's a single terminal status you may rename but not multiply. That constraint keeps “is this finished” answerable across a workspace — worth keeping.
  • Defined at Space, overridable at Folder, Subfolder, and List. Same inheritance chain as everything else.
  • Status templates are saved reusable sets (Kanban, Scrum, Marketing) applied to new containers. Trivial to build, disproportionately good for onboarding — a new user picking “Scrum” instantly has a real workflow.
  • Changing a status set must migrate existing tasks. Deleting a status forces a “move these 43 tasks to…” prompt. Don't skip this; orphaned status references are a bug factory.

Custom field engine

A field definition lives on a container (List, Folder, Space, or Workspace-wide) and consists of a name, a type, and a type_config blob whose shape depends on the type. Values attach to tasks. Here is the full type set from the public API, with the value shape each one stores:

How to store the values

This is the single decision that determines whether filtering stays fast at a million tasks. Three options, in the order I'd consider them:

ApproachFilteringVerdict
JSONB column on taskGIN index; awkward for range and sortFastest to ship, hits a wall on sorted+filtered views
Typed EAV tableIndexed per column; needs a join per filtered fieldRecommended. One row per (task, field) with value_text, value_num, value_date, value_json; index each
Physical columns per fieldNative, fastestDDL at runtime, migration hell, per-tenant schema drift. No.
Derived fields

Formula, rollup, and progress fields are computed, not stored, but views need to filter and sort by them. Compute them on write into a materialized value on the same EAV row, invalidated by the activity log. Computing at read time is what makes these products feel slow.

04.3

View engine — the actual core

A view is a saved query plus a renderer. The incumbent's own API makes this unusually legible: every view, whatever its visual type, serializes to the same object. Build this object, and each new “view type” is a new renderer over an existing query — not a new feature.

View {
  id, name,
  type: list | board | calendar | gantt | timeline | table | workload
      | team | box | activity | map | mind_map | form | doc | chat
      | whiteboard | portfolio,
  parent: { id, type: 7=workspace · 4=space · 5=folder · 6=list },

  grouping: { field: none|status|priority|assignee|tag|dueDate|<custom>,
              dir: 1|-1, collapsed: [], ignore: bool },
  divide:   { field, dir, collapsed: [] },          // swimlanes
  sorting:  { fields: [ { field, dir: 1|-1, idx } ] },

  filters:  { op: AND|OR,
              fields: [ { field, op: EQ|NOT|GT|LT|IN|ANY|ALL|IS_NULL|RANGE,
                          values, idx } ],
              search: "", show_closed: bool },

  columns:  { fields: [ { field, idx, width, hidden, display } ] },

  settings: { show_subtasks: 1=separate|2=expanded|3=collapsed,
              show_task_locations, show_subtask_parent_names,
              show_closed_subtasks, show_assignees, show_images,
              collapse_empty_columns, me_comments, me_subtasks },

  team_sidebar: { assignees: [], assigned_comments, unassigned_tasks }
}

Why this shape is worth copying exactly

  • One compiler, many renderers. Board view is grouping.field = status. Calendar is a date field on an axis. Workload is group by assignee, sum an effort field per time bucket. Table is List with all columns shown. You write the query compiler once.
  • Views attach at any level. The parent.type discriminator is why the same view definition works on one list or across the entire workspace. Your query builder takes a scope (a set of list ids the viewer can see) rather than a single list_id.
  • Personal vs shared. Every view is either saved for everyone or private to its creator, and users can override filters locally without mutating the shared definition. Model this as a base view + per-user overlay.
  • Form and Doc are “views”. Stretching the concept, but it means a form that creates tasks in a list, and a doc pinned to a list, both appear in the same tab bar with the same permissions. Cheap consistency.

04.4

Permission engine

Two orthogonal systems, and conflating them is a classic mistake:

1. Role — what a person may do

RoleCapability
OwnerEverything, including billing and workspace deletion. Can be more than one.
AdminManage members, spaces, and settings; no billing control.
MemberCreate and edit work anywhere they have access.
Limited memberMember without the ability to create top-level containers.
GuestExternal. Sees only explicitly shared objects. Sub-tiered into view-only, comment, and edit.
Custom roleEnterprise feature — a named permission bundle. Ship last.

2. Access — what they may do it to

  • Any container (Space, Folder, Subfolder, List) and individual tasks and docs can be public to the workspace or private, with an explicit grant list of users and groups.
  • Access inherits downward and can be tightened at any level. A workspace setting can flip the default so all new Spaces start private.
  • Guests are granted at the object level — added to a task, a list, or a folder — never given a Space.
  • A “shared with me” query needs to walk the grant graph, which is why the incumbent exposes a dedicated shared hierarchy endpoint. Plan for it.
Implementation

Do not resolve permissions by walking parents at query time — with seven levels of nesting that's seven joins on the hot path. Maintain a materialized access table: (principal_id, list_id, permission), recomputed by a background job whenever a grant or container moves. Every list query then becomes a single inner join, and the “Everything view” becomes trivial.

A data model to start from

Postgres. Abbreviated to the decisions that matter — the ones that are expensive to change later are marked.

                 position, is_private, archived_at)

                 type_config_json, position)

                 value_text, value_num, value_date, value_json,

-- the spine of everything reactive

                 object_id, verb, field, old_value, new_value, at)
                 ← append-only; drives history, notifications, automations

-- satellites
comments        (id, object_kind, object_id, parent_id, author_id,
                 body_json, assigned_to, resolved_at)
time_entries    (id, task_id, user_id, started_at, ended_at,
                 duration_ms, billable, description)
docs / pages    (id, workspace_id, container_id, parent_page_id,
                 title, content_ydoc bytea)          -- CRDT state
automations     (id, container_id, trigger_json, conditions_json,
                 actions_json, enabled, applies_to)
notifications   (id, user_id, activity_id, read_at, cleared_at)

Three details that will save you a rewrite

  • Denormalize the ancestor ids onto tasks. space_id and folder_id on the task row turn every cross-container view from a recursive CTE into an index scan. Maintain them on move.
  • Position as a fractional index (a string or float between neighbors), not an integer. Drag-and-drop reordering with integers means rewriting every row in the list on every drag.
  • Never hard-delete. archived_at everywhere, plus a trash view. Users of this class of tool delete things by accident constantly, and “restore” is table stakes.
07 / Risk

The hard parts

Realtime is two different problems

The most common architectural mistake is picking one strategy for both. They have different consistency requirements:

  • Structured records (tasks, fields, statuses) — server-authoritative. Client writes optimistically to a local cache, server validates and broadcasts a delta to everyone subscribed to that workspace. Conflicts are rare and last-write-wins per field is acceptable. Do not use a CRDT here; you'd be paying enormous complexity to solve a conflict rate near zero, and you'd lose server-side validation.
  • Rich text and canvas (docs, whiteboards, task descriptions) — genuinely concurrent character-level editing. This needs a CRDT (Yjs is the mature choice) with a persistence layer and awareness for cursors. Store the binary doc state; render to HTML on the server for search and previews.

The transport can be shared: one WebSocket per client multiplexing workspace deltas and document updates. Subscriptions are per-container, and the fan-out must be permission-filtered at the server — a naive workspace-wide broadcast leaks private space contents to everyone connected.

The automation engine will try to eat itself

Trigger → conditions → actions is easy. What's hard:

  • Loops. Automation A sets a status, which triggers automation B, which sets a field, which re-triggers A. Every mature system has a depth counter and a per-task execution budget per window. Add both on day one.
  • Actor attribution. Automation-driven changes must be attributable to the automation, not the user who tripped it, or the activity feed becomes a lie and users don't trust it.
  • Idempotency. Consume from the activity log with an outbox pattern and a dedupe key, so a retry doesn't create the same subtask twice.
  • Quotas are the pricing lever. The incumbent gates on runs per month by tier — roughly 100 on free, 1,000, then 10,000. Count runs from the start even if you never charge.

View queries are where performance dies

A single view can filter on three custom fields, sort by a fourth, group by assignee, span every list in the workspace, and be permission-scoped per viewer. Compile it to one parameterized query with the access index joined first (it's the most selective), custom-field filters as EXISTS subqueries against the typed EAV columns, and keyset pagination — never OFFSET, because users scroll deep in a Board column. Cap the filter count, and put a query timeout on it.

Notifications need a hybrid fan-out

Fan-out-on-write (a row per recipient per event) makes the inbox a fast indexed read but explodes on a task with 200 watchers. Fan-out-on-read keeps storage small but makes the inbox a heavy query. Use write fan-out for direct signals (assigned, mentioned, comment replied) and read-time aggregation for ambient activity. Also: digest and collapse. Twelve field edits on one task in a minute is one notification, or your product becomes unusable and people mute it.

Search

Postgres full-text over task names, descriptions, comments, and doc content gets you a long way — with the access index applied as a filter, not as a post-processing step. Move to a dedicated index only when relevance ranking, not latency, becomes the complaint.

Build order

These are genuinely sequential — each phase depends on the one above it. The cut line marks the smallest version that is a real product rather than a demo.

01

Foundation and graph

Auth, workspace, membership. The container tree with arbitrary depth, drag-to-reorder with fractional indices, archive/restore. Tasks with name, status, assignees, dates, priority, parent. The multi-list join table, even though nothing uses it yet.

05

Access control

Private containers, grants, the materialized access index, guests with scoped sharing. Do it before you have real users, because backfilling privacy into an app that assumed everything was visible is a rewrite.

The rule engine with loop guards and quotas. Forms as a view type. Container templates with date offsets. The REST API and webhooks — ideally the same API your own client already uses.

09

AI layer

Only meaningful once there's a real graph to reason over: summarize a list, generate subtasks, fill fields, answer questions across tasks and docs, natural-language view creation. Build it against the same query compiler so AI-generated views are just views.

10 / Product

Positioning notes

Pick a wedge; the engines give you the breadth later

The incumbent's own tiering shows where perceived value sits: the free tier caps storage, spaces, and automation runs; the first paid tier unlocks unlimited views and guests; the next adds workload, advanced dashboards, custom roles, and far higher automation quotas; AI is a separate per-seat add-on. That's a map of what people actually pay for — views, capacity planning, permissions, and automation volume. Note how little of it is “more task fields”.

Where a new entrant can actually win

  • Speed and restraint. The dominant complaint about this category is bloat and slowness. A product with four excellent views that loads instantly beats one with fifteen that doesn't.
  • Opinionated defaults. Infinite configurability means every new workspace starts as a blank, intimidating grid. Ship strong templates that make a workspace useful in one click.
  • One thing done deeply. Agencies, engineering teams, and content teams all use these tools bent into a shape they don't quite fit. Being the one built for a specific shape is a real position.

Building it as your own product

Functionality and architecture are yours to reimplement — hierarchies, saved views, and custom fields are common industry patterns, not anyone's property. What isn't: the name, logo, icon set, brand colors, marketing copy, and verbatim UI text. Write your own copy, design your own visual language, choose an unrelated name, and don't import any of their assets. Ship it as what it is — a work platform you built — and the question of what inspired it never needs to come up.
