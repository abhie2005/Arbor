00 / Name

Arbor

A working name, and a defensible one. The entire product is a tree — workspace, space, folder, list, task, subtask — so the name states the core abstraction rather than describing a benefit. One word, five letters, easy to type in a terminal, reads fine as arbor.dev or arbor.sh, and gives you a mark: a bare branching glyph that works at 16px in a favicon.

Before committing, check the npm name, the GitHub org, the domain, and a basic trademark search in your jurisdiction — there are unrelated companies using the word, which is usually fine across different classes of goods but worth ten minutes of diligence. Alternates in the same register, all short and unclaimed-sounding: Strata, Tract, Rungs, Kiln. Everything below is a find-and-replace away from any of them.

01 / Principles

Six rules that settle most arguments

Design principles are only useful if they can lose you a feature. These can.

PrincipleWhat it rules out
Density is a featureCards with 24px of padding. A row is 31px and shows id, status, title, tags, priority, dates, and assignees without truncating the title. If a screen shows fewer than 20 tasks without scrolling, it's wrong.
Keyboard is the primary inputAny action that exists only behind a hover menu. Every mutation has a shortcut and appears in ⌘K. The mouse is supported, not assumed.
Chrome earns its pixelsDecorative borders, drop shadows on static surfaces, gradient headers, icons next to text that already says the thing. Shadows exist only where something genuinely floats: menus, modals, dragged cards.
Color means state, never decorationColored section headers, rainbow sidebars. Hue is reserved for status group, priority, and one brand accent. If it's colored, it's telling you something.
Optimistic, alwaysSpinners on navigation, "Saving…" toasts, disabled buttons during a write. The UI updates on keypress and reconciles with the server afterwards; failures roll back with an inline, undoable error.
Quiet by defaultNotification badges on everything, celebratory animation, empty-state illustrations. One accent color, used sparingly enough that it still means "here".

04 / Shell

The application shell

Three regions, no global top bar. The sidebar owns the full height, the main column owns its own header, and the detail panel slides in from the right without displacing anything. Every region is independently scrollable, and the main column is the only one that ever moves.

Behaviors that make it feel fast

  • Every cell is editable in place. Click the dot for a status menu, the date for a picker, the avatar stack for assignees. No "edit mode".
  • Row virtualization from day one. Ten thousand tasks scroll at 60fps or the density promise is a lie.
  • Multi-select is first-class. X to select, ⇧J/⇧K to extend, then any field shortcut applies to the whole selection with one optimistic write and one undo entry.
  • The filter bar is the view definition. Each pill maps to one entry in filters.fields[]. Editing a pill on a shared view shows "Unsaved · Save · Reset" rather than silently mutating what your teammates see.
  • New task inline. C or the group "+" inserts an editable row in place, pre-filled with that group's status. Type, hit enter, keep going — the fastest path from thought to task.

10 / Theme

Light theme

Dark-first does not mean dark-only — roughly half of any team will switch, and a light theme that was clearly an afterthought reads as unfinished. Same structure, same density, matched contrast. The accent darkens to #B87514, the selected row uses a pale brass wash instead of a lifted grey, and hairlines get lighter rather than darker so the grid stays quiet.

11 / States

The states nobody designs until they're a bug

StateTreatment
LoadingRow-shaped skeletons at the correct height so nothing shifts when data lands. Never a centered spinner — navigation between views the user has already visited renders from cache instantly and revalidates behind the scenes.
Empty listOne line of text and the inline "+" row already focused. No illustration. The fastest empty state is one you can immediately type into.
Empty because of filtersDistinct from a genuinely empty list: "No tasks match 3 filters · Clear". Confusing these two is a top-five support complaint in this category.
Write failedThe optimistic change rolls back with a brief brass flash on the affected cell and an inline toast: what failed, why, and Retry. No modal, no lost keystrokes.
OfflineA thin bar at the bottom of the sidebar: "Offline · 3 changes queued". Reads keep serving from cache, writes queue, and reconnection replays them in order.
ConflictSomeone else changed the same field while you were editing: keep your value, show a subtle marker on the cell, and let it be inspected in history. Never a blocking "resolve conflict" dialog.
PresenceAvatar stack in the view footer for viewers; a coloured caret with a name label in the editor for co-editing. Presence is ambient — it never moves the layout.
Permission deniedHide what the user cannot see rather than showing a locked row, but make a directly-linked inaccessible task explicit: "You don't have access to this task · Request access".
Archived / trashedArchived items are excluded from views but reachable by key and restorable. Trash keeps items for 30 days with a visible countdown.
12 / Reach

Responsive & accessible

Breakpoints

  • ≥1280px — full three-region shell, detail panel opens beside the list.
  • 1024–1279px — detail panel overlays the main column instead of splitting it.
  • 768–1023px — sidebar collapses to the icon rail; it expands as an overlay on demand.
  • <768px — a genuinely separate layout, not a squeezed desktop. Single column, list and task as full pages, a bottom tab bar for Home / My Work / Inbox / Search, and swipe-to-complete on rows. Board becomes horizontally paged. Do not attempt Gantt or Table on a phone — link out to the list instead.

Accessibility, in a dense keyboard UI specifically

  • Contrast: body text ≥ 4.5:1 and non-text state indicators ≥ 3:1 in both themes. The status dot and the priority flag pair color with shape — a filled versus hollow dot, a flag versus a dash — so the UI survives colorblindness and greyscale.
  • Focus is always visible: a 2px brass ring on every interactive element, plus a persistent row cursor distinct from selection. Keyboard users must never wonder where they are.
  • The list is a real grid: role="grid" with row and cell semantics, aria-selected on rows, and a live region announcing "3 tasks selected" and "Status set to In Progress" so bulk edits are perceivable.
  • Every drag has a keyboard equivalent — reordering, moving between columns, and resizing — because drag-only interactions are the most common accessibility failure in this category.
  • Shortcuts are remappable, and single-letter keys never fire while a text input has focus.
  • Respect prefers-reduced-motion: panel slides and drag animations become instant state changes.
13 / Components

Source the primitive layer from 21st.dev

Do not hand-build menus, date pickers, and command palettes. 21st.dev is a community registry of 12,000+ React components built on Tailwind CSS and Radix primitives, following shadcn/ui conventions. Components install with a single command and the code lands in our repository — we own it, edit it, and ship it as part of the project rather than carrying a runtime dependency.

# once, at repo root — points the registry at packages/ui
npx shadcn@latest init

# per component
npx shadcn@latest add "https://21st.dev/r/<author>/<component>"

Why this registry, specifically

  • Copy-in, not import. The shadcn model puts real source in packages/ui. For an open-source project that's the right shape: contributors can read and change every pixel, there's no version lock, and no upstream release can break the app.
  • Radix underneath. Focus trapping, roving tabindex, ARIA roles, and escape/dismiss behavior are already correct. That delivers a large share of the accessibility requirements for free — and in a keyboard-first product, those are the requirements that matter most.
  • Tailwind CSS variables. The components theme through CSS custom properties, so our token set drops straight in without forking anything.

What to take, and what to leave

Roughly two thousand of the registry's entries are marketing blocks — animated heroes, gradient backgrounds, pricing tables. Those are for a different product surface and none of them belong in a dense application shell. Take the interaction primitives, which are tedious to build and easy to get subtly wrong:

The discipline that keeps it coherent

  1. Re-tokenize on import, once. shadcn's defaults are built for comfortable density — h-10 buttons, py-2 menu items, rounded-lg everywhere. Our targets are a 31px row and a 4px radius. Map the CSS variables to our tokens and override the size scale centrally in packages/ui/tokens.css, not per usage site, or the density drifts component by component until the app looks like every other shadcn project.
  2. Everything lands in packages/ui/src/primitives/. Screens import from @arbor/ui and never from the registry directly. One indirection, and re-skinning the whole app stays a single-package change.
  3. One component per PR, with before/after screenshots in both themes. It's the only review that reliably catches density drift.
  4. Record the provenance. Registry components are community-published and carry their own licenses. On every import, append the source URL, author, and license to packages/ui/ATTRIBUTIONS.md. In an AGPL repository this isn't bookkeeping — an unattributable component is one a downstream adopter can't safely ship.
  5. Reject anything you'd rewrite more than half of. Density is the differentiator. A component that fights the 31px row costs more to tame than to write.

14 / Infra

AWS architecture

One rule governs every choice here: AWS is the reference production deployment, not a dependency. An open-source project that only runs on one cloud gets very few contributors and almost no self-hosters. Every managed service below sits behind an interface with a portable default.

Cost shape

A small deployment — two Fargate tasks per service, one db.t4g.medium, a cache.t4g.micro, an ALB — lands in the low hundreds per month, and the ALB and NAT gateway are a surprisingly large slice. Put NAT behind VPC endpoints for S3 and ECR early; it's the single easiest AWS bill mistake to avoid in this shape.

Nothing sits on a third-party platform

Worth stating plainly, because it's easy to drift: every backend and data service in this project is AWS-managed or self-hosted — no application PaaS, no hosted database vendor, no auth SaaS, no managed queue product outside the account. The app runs in containers you control, the data lives in your RDS instance, and sessions live in your own tables. That keeps the AWS bill the only infrastructure bill, keeps the compliance story to one provider, and — the reason that matters most here — means a self-hoster can run the entire thing without an account anywhere.

If you'd rather run on Google Cloud

The architecture is deliberately generic, so the whole thing ports. Two containers and a Postgres instance is not an AWS-shaped design; it's a portable one that happens to be deployed on AWS first.

Cognito, specifically

Resist making Cognito the primary identity store. It's genuinely awkward to work with, it can't be self-hosted, and putting it on the critical path means nobody can run the project without an AWS account — which forfeits most of the benefit of open-sourcing it. Own the user table; treat every cloud identity provider as an optional federated login on top.

15 / Open source

Building it in the open

License

Recommend AGPL-3.0 for the server, with the client SDK and any shared packages under Apache-2.0. AGPL keeps the code genuinely open and self-hostable while making it impractical for a larger company to run a closed hosted version of your work — the standard posture for open-source products in this category, and the one that preserves the option of selling hosting yourself later. If adoption matters more to you than that protection, MIT is the honest alternative; just decide now, because relicensing after outside contributions arrive requires tracking down every contributor.

Whichever you pick, add a DCO sign-off or a lightweight CLA from the first PR. Retrofitting contributor agreements is genuinely painful.

│  ├─ terraform/    the AWS reference deployment
│  └─ docker/       compose.yml — the self-host path
└─ docs/
   ├─ decisions/    ADRs, numbered, never deleted
   └─ self-hosting/

packages/core is the important one. Keeping the view compiler, permission resolver, and field engine framework-free and fully unit-tested means the three parts of the system that are hardest to get right are also the easiest for a stranger to contribute to — and they stay honest, because they can't quietly reach for a request object.

What earns contributors

  • A README that shows the product in the first screen. A short screen recording of the list view, then the one-line quickstart. Nobody reads paragraph three.
  • docker compose up must genuinely work on a clean machine, with a seeded demo workspace so the first launch shows a populated board rather than an empty shell. Test it in CI on every PR — a broken quickstart is the most expensive bug an open-source project can have.
  • A hosted demo that resets nightly, with no signup. Evaluation before commitment.
  • Real good-first-issues — new view renderers, custom field types, and keyboard shortcuts are perfectly shaped: self-contained, visible, and satisfying.
  • ADRs in docs/decisions. Write down why tasks aren't CRDTs, why the access index is materialized, why Fargate over Lambda. It stops the same debate from recurring and shows outsiders how you think.
  • An architecture diagram in the docs, kept current. The teardown you already have is most of it.
One thing to decide early

Are enterprise features (SSO, audit logs, custom roles) in the open repo or in a separate licensed directory? Both are legitimate — many projects use an ee/ folder under a commercial license — but choosing after those features exist means an awkward, public relicensing. Decide it before you write the first line of SSO.

What to build first

The design above is the target. The build order that reaches it without dead ends:

01

Tokens and primitives, in isolation

Both themes as one token set, then shadcn init pointed at packages/ui and the 21st.dev primitives pulled in and re-tokenized to our density. On top of them, build the pieces that are ours: task row, status dot, avatar stack, priority flag, date chip, tag, pill. Do it in a component workbench before any screen exists — every screen is made of these, and fixing them later means touching everything.

02

The shell and the routing model

Sidebar tree, main header, view tabs, the detail panel as a real route. Get the URL structure right now — panel-as-route versus panel-as-modal is a decision that touches every screen afterwards.

03

List view against the view compiler

Virtualized rows, grouping, inline edit, multi-select, and the filter bar bound to the view definition. This is the phase to over-invest in — Board, Table, and Calendar are renderers over the same machinery, and each costs days instead of weeks once this is right.

04

Keyboard layer and the mutation stack

The command palette, the full shortcut map, and optimistic mutations as invertible operations with real undo. Doing this fourth rather than last is the difference between a keyboard-first product and a product with some shortcuts.

05

Docker compose, seed data, and the README

Before the first public commit. The project's first impression is docker compose up, and it's much easier to keep that working from day one than to repair it at launch.
